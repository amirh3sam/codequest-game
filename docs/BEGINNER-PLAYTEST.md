# Beginner playtest plan

Use this session to learn whether CodeQuest makes first steps in programming clearer and more enjoyable. Do not teach the controls or explain the answers unless the player asks; observe where the interface explains itself and where it does not.

## Participants and setup

- Invite 3–5 people who are new to coding or have only tried a few lessons. One player is useful feedback, not a statistically reliable result.
- Ask each person to use a fresh browser profile and pick a language they have not studied much. Include at least one phone session and one desktop session.
- Allow 30–45 minutes. Tell them the game is a prototype and that they can stop at any time.
- Do not collect names, account details or code from outside the game. Ask before recording a screen; notes without identifying details are enough.

## Give the player these goals

Start with **Start from zero · New to coding**. Observe the instruction-card
puzzle, naming a robot with real code, prediction, the value replay, a guided
charge and the independent rescue. Ask what the second starting-battery check
means. Let the player choose clues naturally; do not explain the answer first.
Record where they first need help and whether they can explain a variable and
`+=` afterward. The chapter's "about 10 minutes" is a design estimate; record
actual times rather than treating the estimate as a test result. Check refresh
resume and downloaded-backup restoration while a draft is unfinished. Then use
the city goals below if time allows. No human sessions have been recorded yet.

1. Start an adventure and explain what each saved row on the title screen represents.
2. Find the first mission, predict the drone battery result, run the code, and repair the drone.
3. Use the tablet to find a lesson or mission, run a short example, and return to the city.
4. Complete as many ordered tasks as time allows. Ask what a variable or code line does in their own words.
5. If they reach the hub: solve the free power preview, describe what each update does, then try the operator signal. Notice that previews do not cost hearts or gems.
6. Download a backup, reload the page, and import the backup. Explain what should happen to their adventures.
7. On mobile, walk to a task and interact with it using touch controls.

Do not require a player to finish eight tasks in the session. Reaching the hub is useful but not necessary to evaluate the mission, lesson and save experience.

## Record observations

For each goal, note whether the player completed it without help, needed a hint, or got stuck. Write down the first place they hesitated and the words they used to describe the problem. Record approximate time to start, first successful run, first accepted task and first use of the tablet or backup controls.

After play, ask for a 1–5 rating for: “I understood what the code was doing,” “I knew what to try next,” and “I wanted to keep exploring.” Then ask: “What was confusing?”, “What felt rewarding?”, and “What would you change first?” Keep answers anonymous.

## Use the results

Look for repeated confusion across participants before changing a lesson or control. Fix a blocker if two people independently hit it; treat preferences from one player as a lead to investigate. Keep the notes and list the next three changes in `docs/PROGRESS.md`. Do not claim the game improved comprehension until beginner sessions support that conclusion.
